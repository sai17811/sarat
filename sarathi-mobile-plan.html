Mobile, responsive layout & 3D load plan

I audited the project you sent. The 3D side is already well optimized, so the biggest wins come from: rendering only when something changes, framing the camera for portrait phones, a static fallback for weak devices, and a real responsive CSS system. Right now there is only one breakpoint, at 820px.

What is already good, and what is missing

doneAlready optimized

  • The 3D chunk is lazy-loaded (next/dynamic, ssr:false, idle callback)
  • WebGL2 check plus high/low device tiers
  • Adaptive DPR via PerformanceMonitor
  • The hall is merged into about 8 draw calls; 216 seats are instanced in 2 draws
  • Baked shadows; the screen texture updates at 30 fps
  • Particles are animated on the GPU; scroll state lives outside React
  • No GLB or image textures; everything is procedural

gapLoad / runtime

  • The render loop runs every frame, even when nothing moves
  • Stars (900 points) are not tiered
  • Additive Beam and rings cause overdraw, which is costly on mobile GPUs
  • Four font families load up front, Telugu included
  • There is no static fallback image when the 3D is skipped

gapLayout

  • Only one breakpoint (820px)
  • Uses 100vh, which jumps under mobile URL bars
  • No safe-area handling (notch, home bar)
  • Camera shots are framed for widescreen and crop badly on portrait phones
  • Giant hero and ghost type sizes on small screens

CSS changes

Viewport & safe areas

  • Replace 100vh with 100svh for reels and 100dvh for the fixed canvas and sheets, keeping vh as a fallback
  • Add viewport-fit=cover and env(safe-area-inset-*) padding on the header, nav and sheet

Type & spacing

  • Lower the hero h1 clamp minimum (for example clamp(48px,14vw,230px))
  • Scale the ghost Telugu text down, or hide it below 480px
  • Move reel padding to tokens: --pad-x and --pad-y per breakpoint

Components

  • Container queries for .nowgrid, .specs and .facts so they adapt to their own width
  • Tap targets of at least 44px (showtimes, seats, rail dots)
  • A draggable booking sheet with snap points (peek, half, full)
  • Tooltips become tap-to-show on touch, via @media (hover:none)

Mobile 3D experience

Portrait camera framing

  • Scale FOV by aspect ratio so the screen width (SW 18) stays in frame: when aspect < 1, widen the vertical FOV
  • Add a SHOTS_PORTRAIT set with the camera pulled back and higher
  • Switch sets on resize or orientation change

Three experience levels

  • Full: desktop and high-tier devices
  • Lite: low-tier devices, with no post or rings, fewer stars, DPR 1, rendered on demand
  • Poster: a static AVIF/WebP render with a "Tap to enter 3D" button. Used for reduced motion, Save-Data, WebGL failure, or very weak devices.

Booking on phones

  • An SVG 2D seat map built from the same seats.ts data, with pinch-zoom
  • An optional "View from seat" button that drives the 3D seat POV
  • It is faster, accessible, and works without WebGL

How we measure

Load

  • Lighthouse mobile and WebPageTest (Moto G4 / 4G profile)
  • Targets: LCP < 2.5s, INP < 200ms, CLS < 0.1
  • First-load JS budget before 3D: < 200 KB gzip

Runtime

  • r3f-perf overlay (draw calls, triangles, GPU ms)
  • Spector.js for frame captures
  • Target: steady 60 fps on a mid-range Android; 30 fps minimum on low-end

Real devices

  • One low-end Android (about 3–4 GB RAM)
  • One recent iPhone (Safari)
  • One tablet in both orientations

Premium curtain-opening intro (covers the loading)

The idea is a theatre-style opening: the curtains part, a spotlight sweeps, and the Sarathi logo glows while the 3D scene and data load behind it. Visitors see a show instead of a spinner.

How it works

  • The curtain is pure CSS/SVG (two velvet panels with gradients and folds, plus a gold logo). It weighs about 5–10 KB and lives in the server-rendered HTML, so it paints immediately and counts as the LCP.
  • While it plays, it preloads in parallel: the 3D chunk (import()), seat and showtime data, and the fonts
  • The curtains open when the scene sends a "ready" signal (first frame rendered), with a minimum of about 1.2s so it always looks intentional
  • The 3D canvas fades in from behind the curtain, and the camera starts with a slow push-in toward the screen

Guardrails

  • Maximum wait of about 3s. If the 3D isn't ready by then, the curtains open onto the poster image and the 3D swaps in later. Users are never held hostage on slow networks.
  • A Skip tap; plays once per session (sessionStorage), with a short 0.6s version on repeat visits
  • prefers-reduced-motion: a simple fade, no curtain motion
  • Animate only transform and opacity (GPU-composited, no layout jank on budget phones)
  • Page text stays in the HTML underneath for SEO and accessibility

Optional polish

  • A soft projector-whirr or orchestral swell, played only after the first tap (browsers block autoplay audio)
  • Gold dust particles drawn in CSS, not WebGL
  • A thin progress line along the curtain hem, driven by real load progress

This fits the 1.5 MB budget: the curtain costs almost nothing, and it buys 1–3s of loading time that the user enjoys instead of waits through.

Decisions

  1. Target devices: all of them: budget Android, mid/high-end phones, tablets and laptops/desktops
  2. Fallback: weak phones get a poster plus "Tap to enter 3D"
  3. Budget: strict, ≤ 1.5 MB first load
  4. Booking: phones get a 2D seat map, with 3D as an optional view
  5. Models (assumed, change if wrong): the scene stays procedural for now, and the GLB pipeline is ready if models arrive
  6. Languages (assumed, change if wrong): Telugu is lazy-loaded as a subset only where it's used, with no Telugu font on first load
  7. Opening: a premium curtain-opening intro that loads the 3D and data behind it
